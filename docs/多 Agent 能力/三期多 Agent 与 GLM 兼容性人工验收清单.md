## 1. 验收目标

- 子 agent 能被主 agent 委派，且其工具调用**不进入**主 agent 上下文（这是本期收益来源）
- markdown agent 定义能被正确加载，三层优先级与降级策略生效
- 子 agent 的防护边界有效：只读、深度上限、预算上限、中断传播
- 配置向导能从厂商真实模型列表中选择，拉取失败时可平滑回退
- GLM 作为非 DeepSeek 厂商可正常工作（含 code plan 套餐端点）
- 未收录模型的费用统计不再静默失效
- TUI 下中文计划审批关键词恢复可用
- 新增用户可见文案无乱码

## 2. 前置准备

1. 确认 node 可用（本机 `/d/nodejs` → `/d/nvm/v22.19.0`）：

```bash
export PATH="/d/nodejs:$PATH"
node --version
```

2. 准备 GLM code plan 套餐的 API Key，写入项目根目录 `.env`（该文件已 gitignore）：

```
CODE_AGENT_API_KEY=你的key
CODE_AGENT_PROVIDER=glm
CODE_AGENT_MODEL=glm-4.6
```

3. 确认项目级 agent 定义存在：

```bash
cat .code-agent/agents/code-explorer.md
```

4. 准备一个全局 agent 定义用于测试优先级（可选，用例 09 需要）：

```bash
mkdir -p ~/.config/code-agent/agents
```

5. 建议准备一个**不在内置价格表中**的模型名（如 `glm-5.3`）用于费用告警验收。

## 5. 重点关注项

1. **上下文隔离是否真的生效**——若子 agent 的工具调用出现在主时间线，本期核心价值即失效
2. 子 agent 是否被赋予了写权限（应当只读）
3. 是否存在递归派生（子 agent 又派子 agent）
4. 委派后父级已渲染的对话是否被清空
5. GLM 零配置调用是否仍出现 429
6. 未收录模型的 token 是否被静默丢弃
7. `task` 参数是否自包含——不自包含时子 agent 会**自信地答错**，这是最难发现的失败模式
8. 向导在各类失败下是否卡死

## 7. 已知限制

以下为本期**有意不做**的部分，不作为验收失败项：

1. **并行执行**未实现。子 agent 串行运行，一次只跑一个。触发重新评估的条件：经常需要在一轮内派 3 个以上互相独立的探索、且每个耗时超 30 秒。
2. **内置价格表不含新模型**。`/models` 端点不返回价格信息，无法自动获取；新模型价格需用户通过 `costGuard.pricing` 自行配置。
3. **深度上限为 1**。子 agent 不能再派生子 agent。
4. **子 agent 默认只读**。写操作需回到主 agent，这是有意的约束（消除并发写冲突与多审批队列问题）。
5. **仓库存在 CRLF 行尾告警**（biome 报约 30 处）。属编辑器/`.gitattributes` 配置层面，与本期改动无关。
6. `glm-4.6` 是推理模型，单次简单问答可能消耗数千 reasoning token，延迟与成本高于非推理模型。探索类子 agent 建议配 `model: fast`。
7. **真实 LLM 集成测试存在偶发失败**（约 1/4 概率）。子 agent 是否能在既定迭代预算内收敛，取决于模型当次的推理路径，无法完全确定。这类测试验证的是「链路能否走通」而非「每次都走通」，重跑即可。

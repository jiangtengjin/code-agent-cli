## 1. 技术选型与决策

### 1.1 技术选型总表

| 层级            | 选型                           | 版本      | 选型理由                                     |
| ------------- | ---------------------------- | ------- | ---------------------------------------- |
| **编程语言**      | TypeScript                   | 5.7+    | 生态丰富、类型安全、CLI 工具成熟（Commander/Ink/Chalk），开发效率高 |
| **运行时**       | Node.js                      | 20 LTS+ | 社区最大、npm 生态全、跨平台支持好                      |
| **CLI 框架**    | Commander.js                 | 12.x    | 最流行的 Node.js CLI 框架，支持子命令、自动帮助、参数解析      |
| **TUI 框架**    | Ink                          | 5.x     | React 组件化渲染终端 UI，支持实时渲染、键盘事件、组件复用        |
| **LLM SDK**   | Vercel AI SDK (@ai-sdk/core) | 4.x     | 统一 Provider 接口、支持 Streaming、Tool Calling、Middleware |
| **MCP SDK**   | @modelcontextprotocol/sdk    | 1.x     | Anthropic 官方 SDK，支持 stdio/SSE/HTTP，持续更新  |
| **配置文件**      | JSONC (jsonc-parser)         | —       | 支持注释和尾逗号，兼容 Cursor/Cline 格式              |
| **包管理**       | pnpm                         | 9.x     | 速度快、磁盘效率高、严格依赖隔离                         |
| **构建工具**      | tsup                         | 8.x     | 基于 esbuild 的 TS 打包器，支持 Tree-shaking、代码分割 |
| **测试框架**      | Vitest                       | 2.x     | 兼容 Jest API、原生 ESM、速度快                   |
| **代码规范**      | Biome                        | 1.x     | 集成了 Lint + Format，比 ESLint + Prettier 快 10x+ |
| **Git Hooks** | husky + lint-staged          | —       | 提交前自动 lint + format                      |

### 1.2 关键设计决策

#### 决策一：为什么选 TypeScript 而非 Rust？

| 维度     | TypeScript        | Rust                |
| ------ | ----------------- | ------------------- |
| 开发速度   | ⭐⭐⭐⭐⭐ 快速迭代        | ⭐⭐⭐ 编译慢、类型系统复杂      |
| 生态丰富度  | ⭐⭐⭐⭐⭐ npm 生态      | ⭐⭐⭐ cargo 生态，CLI 库少 |
| 单文件分发  | ⭐⭐⭐ tsup + pkg    | ⭐⭐⭐⭐⭐ 原生二进制         |
| TUI 开发 | ⭐⭐⭐⭐⭐ Ink (React) | ⭐⭐⭐ ratatui 学习曲线陡   |
| 团队招聘   | ⭐⭐⭐⭐⭐ 开发者多        | ⭐⭐⭐ 国内 Rust 开发者少    |

**结论**：MVP 阶段用 TypeScript 快速验证，后续可考虑用 Rust 重写核心性能敏感模块。

#### 决策二：为什么选 Ink 而非 Neovim-like TUI？

- Ink 基于 React 组件模型，开发效率高
- 状态管理清晰（useState/useEffect）
- 社区组件丰富（ink-text-input、ink-spinner、ink-select-input）
- 与 React 生态共享知识

#### 决策三：LLM Provider 层设计

采用 **Adapter 模式**，统一所有模型接入接口：

```
┌─────────────────┐
│   LLM Provider  │  ← 接口定义
├─────────────────┤
│ OpenAI-compatible│  ← 覆盖 90% 国产模型（DeepSeek/Qwen/GLM/Ollama）
│ Custom Adapter  │  ← 豆包、星火、百度等自研 API
│ Model Router    │  ← 按任务类型自动路由
└─────────────────┘
```

#### 决策四：MCP 集成方式

- 使用官方 `@modelcontextprotocol/sdk`，不自行实现协议
- 工具发现：MCP Server 启动后通过 `listTools` 获取工具列表
- 工具调用：统一封装成和内置工具相同接口，对上层透明

```typescript
// src/tui/hooks/use-chat.ts
export function useChat() {
  const [messages, setMessages] = useState<ChatMessage[]>([]);
  const [mode, setMode] = useState<ChatMode>("normal");
  const [isProcessing, setIsProcessing] = useState(false);

  const sendMessage = async (input: string) => {
    // 1. 检查 Slash 命令
    if (input.startsWith("/")) {
      return handleSlashCommand(input);
    }

    // 2. 添加用户消息
    addMessage({ role: "user", content: input });

    // 3. 处理消息（根据当前模式）
    setIsProcessing(true);
    try {
      await processMessage(input, mode);
    } finally {
      setIsProcessing(false);
    }
  };

  const handleSlashCommand = (input: string) => {
    const [cmd, ...args] = input.slice(1).split(" ");
    switch (cmd) {
      case "mode":
        return setMode(args[0] as ChatMode);
      case "model":
        return setModel(args[0]);
      case "clear":
        return setMessages([]);
      case "usage":
        return showUsage();
      case "help":
        return showHelp();
      case "cost":
        return showCost();
      case "status":
        return showStatus();
      default:
        return addMessage({ role: "system", content: `未知命令: /${cmd}` });
    }
  };
}
```

### 3.4 核心引擎 (`src/engine/`)

#### 3.4.1 会话管理器 (`session.ts`)

核心循环 — **这是整个系统的核心**：

```typescript
export class Session {
  private state: SessionState;
  private llm: LLMProvider;
  private toolRegistry: ToolRegistry;

  constructor(options: SessionOptions) {
    this.state = {
      mode: options.mode,
      model: options.model,
      messages: options.messages,
      tokenUsage: { prompt: 0, completion: 0, total: 0 },
      costEstimate: 0,
    };
    this.llm = createProvider(options.config.model!);
    this.toolRegistry = new ToolRegistry();
  }

  /**
   * 核心处理循环 — 所有模式的统一入口
   */
  async process(input: string): Promise<void> {
    // 1. 添加用户消息
    this.state.messages.push({ role: "user", content: input });

    // 2. 模式特定预处理
    const modeHandler = ModeRouter.getHandler(this.state.mode);
    await modeHandler.beforeProcess?.(this.state);

    // 3. 主循环
    let maxIterations = this.state.mode === "auto" ? 25 : 10;

    for (let i = 0; i < maxIterations; i++) {
      // 3.1 调用 LLM
      const response = await this.llm.chat({
        messages: this.state.messages,
        tools: this.toolRegistry.getToolDefinitions(),
      });

      // 3.2 记录 token 用量
      this.trackUsage(response.usage);

      // 3.3 处理响应
      if (response.toolCalls?.length) {
        // 有工具调用 → 执行工具
        for (const toolCall of response.toolCalls) {
          const result = await this.executeToolCall(toolCall);
          this.state.messages.push({
            role: "tool",
            toolCallId: toolCall.id,
            toolName: toolCall.name,
            content: JSON.stringify(result),
          });
        }
        // 继续循环（Auto 模式可能继续调工具）
        continue;
      } else {
        // 纯文本响应 → 输出并结束
        this.state.messages.push({
          role: "assistant",
          content: response.content,
        });
        this.output(response.content);
        break;
      }
    }
  }

  private async executeToolCall(toolCall: LLMToolCall): Promise<ToolResult> {
    const tool = this.toolRegistry.get(toolCall.name);
    if (!tool) {
      return { success: false, error: `未知工具: ${toolCall.name}` };
    }

    // 显示工具调用 UI
    emit("tool:start", toolCall);

    // 安全检查（写文件/删文件/执行命令需要确认）
    if (tool.requiresConfirm && !this.config.yolo) {
      const confirmed = await userConfirm(toolCall);
      if (!confirmed) {
        return { success: false, error: "用户取消" };
      }
    }

    const result = await tool.execute(toolCall.args);
    emit("tool:end", { toolCall, result });
    return result;
  }
}
```

#### 3.4.2 模式处理逻辑

**Normal 模式**：标准一问一答 + 按需调工具。

```
用户输入 → LLM → 工具调用 → 执行 → 返回结果 → LLM → 文本回复
                                                    → 等待用户下次输入
```

**Auto 模式**（核心 MVP 重点）：

```
用户输入 → LLM → 工具调用 → 执行 → 结果 → LLM → 工具调用 → ...
                                              → 任务完成 → 文本回复
                                                         → 等待用户下次输入
```

Auto 模式下，AI 自主判断任务是否完成。可设置 `maxIterations` 防止无限循环。

**Plan 模式**（V2）：

```
用户输入 → 分析 → LLM → 实施计划（文本）→ 用户确认 → 逐步执行每个步骤
```

**Edit 模式**（V2）：

```
用户输入 → LLM → 工具调用（只允许文件编辑工具）→ 执行 → 展示 diff → 用户确认
```

```typescript
export class ModelRouter {
  private rules: RouteRule[];

  /**
   * 根据任务类型自动选择最优模型
   */
  async route(task: string, userConfig: Config): Promise<LLMConfig> {
    // 1. 用户手动指定 → 直接使用
    if (userConfig.model) return userConfig.model;

    // 2. 检查路由规则
    const taskType = await this.classifyTask(task);
    for (const rule of this.rules) {
      if (rule.matches(taskType)) {
        return this.resolveModel(rule.target, userConfig);
      }
    }

    // 3. 默认模型
    return userConfig.models?.["default"] ?? DEFAULT_MODEL;
  }

  private async classifyTask(task: string): Promise<TaskType> {
    // 用轻量关键词匹配判断任务类型
    if (/生成|创建|写|实现|开发/i.test(task)) return "codegen";
    if (/改|修|重构|优化|重构/i.test(task)) return "refactor";
    if (/读|解|释|分析|查|找/i.test(task)) return "analysis";
    if (/bug|错|修|调|试|修复/i.test(task)) return "debug";
    return "general";
  }
}
```

```typescript
export const editFileTool: ToolDefinition = {
  name: "edit_file",
  description: "精确编辑文件内容（搜索替换）",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string", description: "文件路径" },
      oldString: { type: "string", description: "需要替换的原始文本" },
      newString: { type: "string", description: "替换后的新文本" },
    },
    required: ["path", "oldString", "newString"],
  },
  requiresConfirm: true,
  async execute(args) {
    const { path, oldString, newString } = args as EditArgs;
    const content = await fs.readFile(path, "utf-8");

    if (!content.includes(oldString)) {
      return {
        success: false,
        error: `在 ${path} 中未找到匹配的文本。前 100 个字符: "${content.slice(0, 100)}"`,
      };
    }

    const newContent = content.replace(oldString, newString);
    await fs.writeFile(path, newContent, "utf-8");

    return {
      success: true,
      data: { path, diff: generateDiff(content, newContent) },
    };
  },
```

```typescript
export class MCPClient {
  private transport: Transport;
  private client: Client;

  constructor(config: MCPServerConfig) {
    switch (config.transport ?? "stdio") {
      case "stdio":
        this.transport = new StdioClientTransport({
          command: config.command,
          args: config.args,
          env: config.env,
        });
        break;
      case "sse":
        this.transport = new SSEClientTransport(new URL(config.url!));
        break;
      case "http":
        this.transport = new HTTPClientTransport(config.url!);
        break;
    }
    this.client = new Client(this.transport);
  }

  async connect(): Promise<void> {
    await this.client.connect();
  }

  async listTools(): Promise<MCPServerTool[]> {
    const result = await this.client.listTools();
    return result.tools;
  }

  async callTool(
    name: string,
    args: Record<string, unknown>,
  ): Promise<ToolResult> {
    const result = await this.client.callTool({ name, arguments: args });
    return this.parseResult(result);
  }
```

```
        │       ├── 调用 API
        │       └── 返回 LLMResponse
        │
        ├── 4. 检查 response.toolCalls?
        │       │

        │       │   │       │

        │       │   │       ├── 搜索 → glob/grep
        │       │   │       ├── MCP → MCPClient.callTool()
        │       │   │       └── 终端 → node-pty (V2)
        │       │   │
        │       │   └── 添加 { role: 'tool', content: result } 到 messages
        │       │
        │       └── 无工具调用：
        │               │
        │               └── 添加 { role: 'assistant', content } 到 messages
        │
```

### 4.2 Auto 模式 vs Normal 模式的区别

| 阶段   | Normal               | Auto                     |
| ---- | -------------------- | ------------------------ |
| 循环次数 | 1 次 LLM 调用 + 1 轮工具执行 | 最多 25 轮 LLM 调用           |
| 结束条件 | LLM 返回文本回复           | LLM 返回文本回复 或 AI 自主判断完成   |
| 工具确认 | 每次都确认                | `--yolo` 跳过确认，否则同 Normal |
| 用户介入 | 每次工具调用后等待用户          | 一次性分配任务，AI 自主完成          |

### 8.2 MVP 端到端验证场景

#### 场景：让 AI 修改代码

```
用户输入：
  "给 src/api.ts 中的 fetchUsers 函数添加错误处理"

系统执行：
  1. Normal 模式，进入 Session.process
  2. LLM(DeepSeek-Coder) 收到消息 + 工具列表
  3. LLM 决定：先读取文件 → 调用 read_file
     → TUI 显示 "📂 read_file: src/api.ts"
     → 读取文件内容，返回给 LLM
  4. LLM 分析代码，决定编辑 → 调用 edit_file
     → TUI 显示 "✏️ edit_file: src/api.ts"
     → 用户确认？→ Y
     → 执行替换，返回 diff
  5. LLM 回复修改完成，展示修改内容
  6. TUI 显示最终回复

结果：代码已修改，用户看到 diff 和 AI 说明
```

#### 场景：用 Auto 模式自主完成重构

```
用户输入：
  "把项目中所有 var 改为 const/let，确保语义正确"

系统执行：
  1. Auto 模式，设置 maxIterations = 25
  2. LLM 自主规划：查找所有包含 var 的文件
     → grep_search "\\bvar\\b" → 返回文件列表
  3. 逐个文件分析、修改
     → read_file → 分析 → edit_file → 确认 → 下一个
  4. 所有文件改完 → LLM 判断任务完成
  5. 回复修改总结

结果：无需用户逐一手动确认每个修改（--yolo 模式）
```

### 8.3 技术预研重点（开始编码前必须明确的点）

1. **LLM Tool Calling 格式兼容性**：确认 DeepSeek-Coder / Qwen-Coder / GLM-4 的 Function Calling 返回格式与 OpenAI 的兼容程度，需实际测试
2. **MCP stdio 通信**：确认 MCP JSON-RPC 消息格式和生命周期管理
3. **Ink 键盘事件**：确认 TextInput + 自定义快捷键（Tab 切换模式）的实现方式
4. **配置合并策略**：deepMerge 的边界情况（数组合并、undefined 处理等）

```typescript
export class MockLLMProvider implements LLMProvider {
```

## 10. 风险与应对

| 编号   | 风险                            | 可能性  | 影响   | 应对                                       |
| ---- | ----------------------------- | ---- | ---- | ---------------------------------------- |
| R1   | DeepSeek Function Calling 不稳定 | 中    | 高    | 备选方案：先用 Qwen-Coder（Function Calling 最成熟），兼容多家 |
| R2   | Ink 的 React 并发模式兼容问题          | 低    | 中    | 锁定 Ink 版本，关注 React 19 兼容性                |
| R3   | MCP stdio 子进程管理复杂             | 中    | 中    | 先支持 stdio，SSE/HTTP 延后；做好进程生命周期管理         |
| R4   | Windows 终端兼容性                 | 高    | 中    | MVP 优先 macOS/Linux，Windows 做基本兼容（彩色输出降级） |
| R5   | Token 消耗超出预期                  | 中    | 中    | Auto 模式严格限制 maxIterations；提供 /cost 命令透明展示 |
| R6   | 用户 API Key 泄露                 | 低    | 高    | 配置文件中支持 env 变量引用，不明文存储 Key               |

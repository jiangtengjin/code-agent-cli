# Code Agent CLI 二期会话能力设计方案

> 版本：v1.0  
> 日期：2026-07-25  
> 状态：方案评审稿  
> 参考产品：Claude Code、OpenAI Codex CLI  
> 适用范围：Code Agent CLI Phase 2 Session 能力

---

## 1. 背景与目标

一期已经完成以下核心闭环：

- 本地 CLI 对话
- Normal / Auto / Plan / Edit 模式
- 内置工具与 MCP 工具调用
- Slash 命令
- 基础 usage / cost / plan 状态管理

当前缺失的是“会话持续性”：

- 退出后无法恢复上次对话
- `/clear` 只能清空内存，不能形成新旧会话边界
- 无法列出历史会话
- 无法在多个任务上下文之间切换
- 中断后无法明确知道这次任务是否可恢复、恢复到哪里

本期目标是补齐会话能力，而不是重做 TUI。设计参考以 `Claude Code` 与 `Codex CLI` 为主，采用“本地优先、工作区优先恢复、会话历史与长期记忆解耦”的产品路线。

---

## 2. 竞品结论与采纳策略

### 2.1 Claude Code / Codex 的共同模式

两者虽然命令风格不同，但核心模式高度一致：

- 会话持久化为本地数据，而不是依赖服务端保存
- 默认只在当前工作区内恢复最近会话
- 同时提供“快速继续最近一次”和“打开会话选择器”两条入口
- 会话历史与长期记忆分开设计
- 支持会话生命周期操作，如 resume、fork、archive

### 2.2 本方案明确采纳的模式

本期明确采纳以下模式：

1. `当前工作区优先`
   - 默认只列出当前工作区的历史会话
   - 跨工作区检索必须显式开启

2. `本地持久化`
   - 所有会话数据保存在本机
   - 二期不做账号同步、云端会话托管

3. `双入口恢复`
   - 快捷恢复最近会话
   - 列表式选择任意历史会话

4. `会话生命周期`
   - resume
   - fork
   - archive / unarchive

5. `历史会话与长期记忆解耦`
   - 二期只做 session
   - 不把“长期偏好 / 项目规范 / 记忆”混进 transcript 方案

### 2.3 本期不采纳的模式

以下能力不放入二期范围：

- 云同步
- 多设备共享会话
- 基于向量检索的历史语义搜索
- 自动长期记忆
- 完整 Ink/TUI 重构
- Gemini 风格的 checkpoint / rewind

说明：

- `checkpoint / rewind` 是值得后续评估的增强能力，但它会牵涉“对话回退”和“代码回退”的双重语义，复杂度明显高于本期目标。

## 3. 产品范围

### 3.1 目标能力

二期交付以下能力：

- 自动创建和持久化本地会话
- 支持 `--continue` 恢复当前工作区最近会话
- 支持 `resume` 子命令按会话 ID / 名称恢复
- 支持 `/resume` 查看当前工作区历史会话并切换
- 支持会话摘要、标题、最近活动时间展示
- 支持 `fork` 派生新会话
- 支持 `archive` 隐藏旧会话
- 支持中断后保留会话并标记可恢复状态
- 支持恢复 `messages`、`mode`、`pendingPlan`、`usage/cost` 等运行态

### 3.2 非目标能力

- 云端会话管理后台
- 多人共享会话
- 会话权限协作
- 历史会话全文检索
- Agent 自动记忆偏好
- 代码快照回滚

## 4. 核心产品决策

### 4.1 会话作用域

采用 `工作区作用域优先`。

工作区定义：

- 若当前目录位于 Git 仓库中，则以 `git root` 作为工作区根目录
- 否则以当前 `cwd` 作为工作区根目录

原因：

- 符合 Claude / Codex 的“当前仓库优先恢复”心智
- 能避免不同项目历史混杂
- 能保证 `/resume` 的结果足够短、足够准

### 4.2 会话存储策略

采用 `本地文件存储 + 会话索引 + transcript 日志`。

原因：

- 当前项目已经有本地 config 体系，延续本地存储实现成本最低
- 便于调试、迁移和故障恢复
- 不要求引入数据库

### 4.3 交互入口

参考 Claude 与 Codex，提供两类入口：

1. 快速继续
   - `code-agent --continue`
   - 恢复当前工作区最近的交互式会话

2. 显式恢复
   - `code-agent resume`
   - `code-agent resume --last`
   - `code-agent resume <session-id-or-name>`
   - `/resume`

### 4.4 非交互任务的纳入策略

参考 Codex，二期默认 `不把 --prompt 会话展示在普通 /resume 列表中`，但底层允许持久化。

建议策略：

- `kind = interactive`：默认参与 `/resume`、`--continue`
- `kind = prompt`：默认不参与
- 后续可增加 `--include-non-interactive` 开关

原因：

- 交互会话和批处理会话的恢复诉求不同
- 默认混在一起会降低列表可读性

### 4.5 长期记忆处理

二期显式不做“长期记忆”。

会话历史只解决：

- 我上次聊到了哪
- 我上次跑到了哪
- 我能不能继续这次任务

它不解决：

- agent 应长期记住哪些团队规范
- agent 应长期记住哪些用户偏好

后续如需类 `CLAUDE.md / AGENTS.md` 能力，应单独立项。

## 5. 用户体验设计

### 5.1 新建会话

启动 `code-agent` 时：

- 不立即创建会话
- 第一次收到非 slash 用户输入时创建会话

原因：

- 避免大量空会话
- 更符合“有实际任务才创建 session”的产品语义

### 5.2 快速恢复最近会话

命令：

```bash
code-agent --continue
```

行为：

- 只查询当前工作区
- 只查询 `interactive`
- 只查询 `non-archived`
- 恢复最近活动时间最新的一条

若无可恢复会话：

- 输出提示并创建新会话进入正常聊天

### 5.3 显式恢复会话

命令：

```bash
code-agent resume
code-agent resume --last
code-agent resume abc123
code-agent resume "fix-auth-timeout"
code-agent resume --all
code-agent resume --fork abc123
```

建议行为：

- `resume` 无参数：进入列表选择
- `resume --last`：恢复当前工作区最近会话
- `resume <id|name>`：按 ID、标题前缀精确匹配
- `resume --all`：跨工作区检索
- `resume --fork`：基于目标会话派生新会话而不是直接接管原会话

### 5.4 会话列表体验

二期不做完整 TUI，但提供轻量列表选择器。

建议展示字段：

- 序号
- 标题
- 状态
- 模式
- 最近活动时间
- turn 数
- 工作区标识
- 是否为 archived / interrupted

建议列表排序：

- 默认按 `lastActiveAt desc`

建议默认过滤：

- 当前工作区
- interactive
- 非 archived

### 5.5 Slash 命令

二期新增或扩展以下命令：

```text
/resume                 打开当前工作区历史会话列表
/resume <query>         恢复指定会话
/session                查看当前会话摘要
/fork [name]            基于当前会话派生新会话
/archive                归档当前会话并开始空白会话
/unarchive <query>      取消归档目标会话
```

说明：

- `/clear` 的语义保持为“清空当前上下文”，不替代 archive
- `/resume` 与 `/fork` 只允许在 `idle` 状态执行

### 5.6 标题与摘要

二期建议采用 `确定性生成`，不引入额外模型调用：

- 标题：取第一条 user message 的前 40~60 个可见字符
- 摘要：取最近一次 user message 与 assistant message 的短预览

后续如需更好的人类可读标题，再考虑异步 LLM 摘要。

原因：

- 避免额外费用
- 避免标题生成失败影响主链路

## 6. 会话模型设计

### 6.1 Session 核心对象

建议新增 `src/types/session.ts`：

```ts
export type SessionKind = "interactive" | "prompt";

export type SessionStatus =
  | "idle"
  | "running"
  | "awaiting_plan_approval"
  | "interrupted"
  | "archived";

export interface SessionSummary {
  id: string;
  kind: SessionKind;
  title: string;
  workspaceKey: string;
  workspacePath: string;
  status: SessionStatus;
  mode: ChatMode;
  createdAt: string;
  updatedAt: string;
  lastActiveAt: string;
  turnCount: number;
  archivedAt?: string;
  parentSessionId?: string;
  latestUserPreview?: string;
  latestAssistantPreview?: string;
}

export interface SessionState {
  sessionId: string;
  kind: SessionKind;
  mode: ChatMode;
  messages: LLMMessage[];
  pendingPlan?: PlanState;
  usage: UsageSnapshot;
  cost?: CostSnapshot;
  status: SessionStatus;
  workspaceKey: string;
  workspacePath: string;
  createdAt: string;
  updatedAt: string;
  lastActiveAt: string;
  title: string;
  parentSessionId?: string;
}
```

### 6.2 会话状态机

建议状态机如下：

```text
new
  -> idle
idle
  -> running
running
  -> idle
running
  -> awaiting_plan_approval
awaiting_plan_approval
  -> running
awaiting_plan_approval
  -> idle
running
  -> interrupted
idle
  -> archived
interrupted
  -> idle
archived
  -> idle
```

关键约束：

- `running` 时不允许 `/resume`、`/fork`、`/archive`
- `interrupted` 代表“会话保留，但上一轮未完整结束”
- `archived` 会话默认不出现在普通列表里

### 6.3 fork 语义

`fork` 的语义参考 Codex / Claude branch：

- 新建一个 session
- 复制父会话的 `messages`
- 复制父会话的 `pendingPlan`
- 标记 `parentSessionId`
- 新会话的 `usage / cost` 统计从 0 开始

原因：

- fork 是“基于既有上下文开启新分支”
- 不是“把旧账也算进新会话”

## 7. 存储结构设计

### 7.1 存储目录

二期建议沿用现有本地 config 根目录，新增 session store：

```text
~/.config/code-agent/
  config.jsonc
  sessions/
    index.json
    sessions/
      <session-id>/
        meta.json
        state.json
        transcript.jsonl
```

说明：

- 二期优先与现有配置路径保持一致
- 后续如需迁移到更标准的 data 目录，可单独做 path migration

### 7.2 文件职责

`index.json`

- 全局会话索引
- 用于列表查询和快速过滤
- 只保存 `SessionSummary[]`

`meta.json`

- 相对稳定的会话元信息
- 例如 `id / workspace / createdAt / parentSessionId`

`state.json`

- 当前可恢复运行态
- 包含 `mode / messages / pendingPlan / usage / cost / status`

`transcript.jsonl`

- 追加式 transcript
- 作为审计和恢复依据

### 7.3 transcript 事件结构

建议 `transcript.jsonl` 以事件形式记录：

```ts
type SessionEvent =
  | { type: "message"; createdAt: string; message: LLMMessage }
  | { type: "status"; createdAt: string; status: SessionStatus; reason?: string }
  | { type: "plan"; createdAt: string; planState: PlanState | null }
  | { type: "fork"; createdAt: string; parentSessionId: string }
  | { type: "archive"; createdAt: string }
  | { type: "resume"; createdAt: string; fromSessionId?: string };
```

说明：

- `state.json` 负责快速恢复
- `transcript.jsonl` 负责可追踪性
- 二期不额外拆 `tool-start / tool-end` 审计文件，避免过度设计

### 7.4 写入策略

建议采用以下策略：

1. 每次消息追加时 append `transcript.jsonl`
2. 每轮任务结束后原子写入 `state.json`
3. 每次会话摘要变化后原子写入 `index.json`

原子写建议：

- 先写入临时文件
- 再 rename 替换目标文件

原因：

- 可降低异常退出导致的损坏概率

## 8. 运行时集成设计

### 8.1 与当前代码结构的关系

当前核心链路为：

```text
src/cli/chat.ts
  -> src/modes/*
  -> src/session/execution.ts
```

二期建议新增：

```text
src/session/
  store.ts
  index.ts
  workspace.ts
  runtime.ts

src/types/
  session.ts
```

职责拆分：

- `workspace.ts`
  - 解析当前工作区根目录与 workspaceKey

- `store.ts`
  - 读写 `index/meta/state/transcript`

- `runtime.ts`
  - 管理当前会话对象与状态迁移

- `chat.ts`
  - 只负责交互与 slash 命令分发

### 8.2 Chat 启动时的行为

`startChat(config)` 增强为：

1. 创建 `SessionStore`
2. 判断是否传入 `--continue`
3. 判断是否传入 `resume` 子命令
4. 如果需要恢复，则加载目标 `SessionState`
5. 将 `messages / pendingPlan / mode / usageTracker / costTracker` 注入运行时
6. 渲染欢迎区时显示当前会话 ID / 标题 / 状态

### 8.3 执行循环中的持久化钩子

当前 `runExecutionLoop` 会直接修改：

- `context.messages`
- `context.usageTracker`
- `pendingPlan`

二期建议在 `RunContext` 中增加轻量钩子：

```ts
onMessagesChanged?: (messages: LLMMessage[]) => Promise<void> | void;
onStatusChanged?: (status: SessionStatus) => Promise<void> | void;
onPlanStateChanged?: (plan?: PlanState) => Promise<void> | void;
```

这样：

- `execution.ts` 保持对 session store 无感
- `chat.ts / runPrompt()` 可在外层注入持久化逻辑

### 8.4 `/clear` 的兼容策略

为保持兼容，`/clear` 仍然保留，但语义需要明确：

- 清空当前内存上下文
- 保留当前 session 记录
- 在 transcript 中记录一次 `status` / `clear` 事件

推荐实现：

- `/clear` 后仍保留当前 sessionId
- 但 `messages` 清空，`pendingPlan` 清空

说明：

- 这样不破坏一期既有心智
- 真正“结束旧会话”的动作交给 `/archive`

## 9. 中断与恢复语义

### 9.1 中断场景

二期需要区分三种中断：

1. `idle` 状态下退出
   - 正常退出，session 保持 `idle`

2. `running` 状态下单次 `Ctrl+C`
   - 尝试中断当前请求
   - 将 session 标记为 `interrupted`
   - 保存当前 `state.json`

3. `running` 状态下连续两次 `Ctrl+C`
   - 强制退出
   - 尽最大努力写入 `interrupted` 状态

### 9.2 Provider / Tool 的取消能力

二期建议引入 `AbortController`，但按“尽力而为”处理：

- LLM Provider：优先支持 abort signal
- 内置工具：可逐步支持
- MCP 工具：默认不保证可取消

关键产品约束：

- 被中断的工具调用不自动重放
- 恢复会话后只恢复“上下文”，不自动继续执行上一个被打断的副作用工具

原因：

- 文件写入、终端命令、外部 MCP 调用可能已经产生部分副作用
- 自动重放有重复执行风险

### 9.3 恢复 interrupted 会话后的表现

恢复 interrupted 会话时：

- 顶部提示该会话上一次被中断
- 若上一次停在 `awaiting_plan_approval`，则恢复该状态
- 若上一次停在普通 `running`，则恢复为 `idle`
- 插入一条本地系统提示，说明“上一轮执行被中断，请用户决定是否继续”

建议不要自动补发最后一条用户消息。

## 10. 命令设计

### 10.1 CLI 层

建议新增：

```bash
code-agent --continue

code-agent resume <query>
code-agent resume --all
code-agent resume --fork <query>
```

建议新增 Commander 结构：

```text
code-agent
  --continue

    --last
    --all
    --fork
```

优先级建议：

- `resume` 子命令优先于默认 chat 动作
- `--continue` 只作用于默认 chat 入口

### 10.2 Slash 层

建议扩展命令补全与帮助输出：

- `/resume`
- `/session`
- `/fork`
- `/archive`
- `/unarchive`

## 11. 配置设计

建议新增配置块：

```jsonc
{
  "sessions": {
    "enabled": true,
    "storePath": "~/.config/code-agent/sessions",
    "defaultScope": "workspace",
    "includePromptSessions": false
  }
}
```

字段说明：

- `enabled`
  - 是否启用本地会话持久化

- `storePath`
  - 会话存储目录

- `defaultScope`
  - 当前仅支持 `workspace`

- `includePromptSessions`
  - 是否默认把 `--prompt` 会话纳入 resume 列表

默认建议：

- `enabled = true`
- `includePromptSessions = false`

新增测试覆盖：

- index 过滤与排序
- state / transcript 读写
- fork / archive 状态流转

### 12.2 集成测试

新增 CLI 测试覆盖：

- 首次聊天自动创建 session
- `--continue` 恢复当前工作区最近会话
- `resume <id>` 恢复指定会话

### 12.3 破坏性边界测试

重点验证：

- 写入过程中进程退出
- transcript 存在脏行
- index 与 state 不一致
- interrupted 会话恢复

容错建议：

- `state.json` 损坏时可回退到 transcript 重建
- 单个 session 损坏不应阻塞整个会话列表

## 14. 风险与对策

### 风险 1：会话文件膨胀

问题：

- 长会话会导致 `messages` 和 transcript 增大

对策：

- 二期先接受增长
- 三期评估 `/compact` 或 transcript compaction

### 风险 2：中断时状态不一致

问题：

- 运行中的工具可能已经部分生效

对策：

- interrupted 后不自动重放工具
- 恢复后交由用户决定下一步

### 风险 3：现有 chat.ts 继续膨胀

问题：

- 现有 `chat.ts` 已承担较多职责

对策：

- session store 与 session runtime 独立成模块
- slash 命令处理逐步下沉

---

## 15. 推荐结论

参考 Claude / Codex，本项目二期应采取以下主线：

1. 先做 `本地会话持久化`
2. 默认按 `当前工作区` 恢复
3. 提供 `--continue + resume + /resume` 双入口
4. 将 `fork / archive` 纳入会话生命周期
5. 将 `历史会话` 与 `长期记忆` 严格拆开
6. 不在二期引入完整 TUI 和云同步

这条路线的优点是：

- 与主流产品心智一致
- 与当前代码结构兼容
- 能最快补齐真实可用的会话能力
- 不会因为 UI 重构而拖慢交付

## 16. 待确认项

以下事项建议在评审时确认，但本方案已给出推荐默认值：

1. 是否默认持久化 `--prompt` 会话
   - 推荐：持久化，但默认不展示在普通 `/resume`

2. `/archive` 后是“退出”还是“开启新空会话”
   - 推荐：开启新空会话，避免强制退出

3. 是否在二期加入 `unarchive`
   - 推荐：CLI 可延后，先保留 slash 能力或仅实现内部 store

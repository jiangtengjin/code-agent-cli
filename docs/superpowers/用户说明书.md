# Superpowers 超级技能 — 傻瓜式入门手册

> 本仓库已安装 superpowers 插件。所有技能（skills）通过 `skill` 工具加载使用。
> 配置文件：项目根目录 `opencode.json`

---

## 📖 快速入门（30 秒学会）

### 核心规则：一句话

> **遇到任何任务，怀疑所有技能，先用 `skill` 工具加载试试。**

### 如何加载技能？

```
用 skill 工具，告诉我要加载哪个技能
```

例如对 AI 说：
> "加载 brainstorming 技能"
> "用 TDD 技能来做这个功能"
> "帮我 debug，加载 systematic-debugging 技能"

## 🧭 技能全景图

本仓库已安装以下 18 个技能，分为三大类：

### 一、🧠 想清楚再做（流程类）

| 技能 | 什么时候用 | 一句话说明 |
|------|-----------|-----------|
| **brainstorming** | 做新功能/新项目前 | 先聊需求→出方案→写设计文档→再动手 |
| **writing-plans** | 设计确定后 | 把设计拆成一步步可执行的任务计划 |
| **executing-plans** | 拿到计划后 | 按计划一步步执行，批量跑任务 |
| **subagent-driven-development** | 有计划的复杂项目 | 派子代理并行执行每个任务，做完自动 review |

### 二、🔨 干活工具（开发类）

| 技能 | 什么时候用 | 一句话说明 |
|------|-----------|-----------|
| **test-driven-development (TDD)** | 任何时候写代码 | 先写测试→看它失败→写代码让它通过→重构 |
| **systematic-debugging** | 遇到 bug | 先找根因→再修，不许瞎猜 |
| **verification-before-completion** | 任务做完时 | 跑测试验证通过之前，不许说"搞定" |
| **requesting-code-review** | 代码写完后 | 派一个独立代理来审查你的代码 |
| **receiving-code-review** | 收到 review 反馈时 | 先验证再改，不要无脑说"你说得对" |
| **dispatching-parallel-agents** | 多个独立 bug 要修 | 同时派多个代理各自修一个，并行干活 |
| **writing-skills** | 想创建自己的技能 | 像写代码一样 TDD 来写技能文档 |
| **just-scrape** | 需要搜索/爬取网页 | 搜网页、抓内容、提取结构化数据 |

### 三、🔄 流程衔接（收尾/协作类）

| 技能 | 什么时候用 | 一句话说明 |
|------|-----------|-----------|
| **finishing-a-development-branch** | 功能开发完成 | 验证测试→选方案（合并/PR/保留/丢弃） |
| **using-git-worktrees** | 开始新功能前 | 创建工作隔离区，不影响主分支 |
| **sync-push** | 要推送代码 | 同步主干→合并→推送 |
| **find-skills** | 想找更多技能 | 从公开技能市场搜索安装 |
| **customize-opencode** | 想改 opencode 配置 | 编辑配置文件/agent/插件/MCP |
| **using-superpowers** | 刚上手时 | 本手册就是这个技能的说明 |

## 💡 使用方法示例

### 例 1：构建一个功能完整流程

**你：**
> "帮我设计一个用户登录功能"

**AI 会：**
1. 加载 `brainstorming` 技能
2. 先问你：什么类型的登录？邮箱密码/OAuth/手机号？
3. 确认后提出 2-3 种方案
4. 你选定方案后，写设计文档
5. 然后加载 `writing-plans` 拆任务
6. 最终用 `subagent-driven-development` 或 `executing-plans` 实现

### 例 2：修复一个 bug

**你：**
> "登录按钮点不动，帮我修"

**AI 会：**
1. 加载 `systematic-debugging` 技能
2. 先找根因：看报错→复现→检查最近改动→追踪调用链
3. 找到根因后，用 TDD 写测试→修代码→验证
4. 最后用 `verification-before-completion` 确认修复

## ⚠️ 避坑指南

| 错误想法 | 正确做法 |
|---------|---------|
| "这很简单，直接写代码吧" | 先加载 brainstorming 聊清楚，避免返工 |
| "我先写代码，回头补测试" | 用 TDD：先测试再代码，看到测试失败才算数 |
| "我猜是 X 的问题，先修了" | 用 systematic-debugging：先找根因再修 |
| "应该没问题了" | 用 verification-before-completion：跑测试验证 |
| "我来手动改配置" | 用 customize-opencode，schema 会自动校验 |

## 🔄 完整工作流（最佳实践）

```
开始新功能
  ├─ ❶ using-git-worktrees（可选：创建工作隔离区）
  ├─ ❷ brainstorming（设计方案，写 spec）
  ├─ ❸ writing-plans（拆解任务计划）
  ├─ ❹ subagent-driven-development 或 executing-plans（执行）
  │    └─ 每个任务：TDD → 代码审查
  ├─ ❺ verification-before-completion（验证全部通过）
  └─ ❻ finishing-a-development-branch（合并/PR/保留/丢弃）

日常修 bug
  ├─ ❶ systematic-debugging（定位根因）
  ├─ ❷ TDD 修复（测试先行）
  └─ ❸ verification-before-completion（确认修复）

推送代码
  └─ sync-push（自动同步→合并→推送）
```
